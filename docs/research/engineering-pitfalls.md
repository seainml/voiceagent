## 一、端到端延迟预算表

从"用户说完最后一个音素"到"听到第一个音素"（TTFA / TTFW）。可复用的分解式（论文原文）：**TTFA = endpointing/VAD + ASR 终结算 + LLM 首块(TTFT) + TTS 首个音频 + playout/jitter**（[arXiv 2603.29893](https://arxiv.org/html/2603.29893)）**[已核实：公式原文]**。

| 环节 | 典型值 | 优化手段 | 参考来源 |
| --- | --- | --- | --- |
| **VAD 静音判定** | **300–700 ms**；Azure 官方区间 100–5000 ms、**500 ms 为常见默认**；本项目 `silence_ms=700` | 缩短固定窗；改用语义 endpointing，语义完整即切 | [Azure](https://learn.microsoft.com/fr-fr/azure/ai-services/speech-service/how-to-recognize-speech?view=foundry-classic)、[LiveKit](https://docs.livekit.io/agents/logic/turns/tuning/) |
| **ASR 终结** | 流式 100–300 ms；论文 STT 项 **≈400 ms**；批式 **0.5–3 s 且全串行** | 流式 ASR + interim，endpoint 前就把 partial 喂 LLM | [论文预算式](https://ar5iv.labs.arxiv.org/html/2603.05413)、[Deepgram](https://developers.deepgram.com/docs/understand-endpointing-interim-results) |
| **LLM 首 token** | 200–500 ms；论文"首句"项 **≈300 ms**；大模型/长 prompt 500–900 ms | 流式输出；压缩 prompt；prompt caching；首句用小模型 | [论文预算式](https://ar5iv.labs.arxiv.org/html/2603.05413) |
| **句子切分** | 首包额外 **50–200 ms** | 首包按标点/短子句切（8–12 字），后续按长句切 | [经验区间] |
| **TTS 首包** | 75–300 ms（低延迟流式）；300–800 ms（高保真） | 选流式 TTS；预建连接 | [ElevenLabs](https://elevenlabs.io/blog/text-to-speech-api-up-to-40-faster-globally) |
| **网络 RTT** | 同区 20–80 ms；跨区 150–400 ms | 边缘部署；ASR/LLM/TTS 与媒体服务器同区 | [LiveKit](https://livekit.com/blog/why-webrtc-beats-websockets-for-voice-ai-agents) |
| **播放/抖动缓冲** | 40–200 ms；可实测 `RTCInboundRtpStreamStats.totalProcessingDelay` | 只保留一层缓冲，勿在应用层再叠 | [MDN](https://developer.mozilla.org/en-US/docs/Web/API/RTCInboundRtpStreamStats/totalProcessingDelay) |
| **首句合计（优化前/后）** | **1.2–2.0 s / 500–800 ms**；另有同行评议工作测得真实 agent **~2.7 s 中位**并指出"超出 G.114" | — | [ACL 2026 demo](https://aclanthology.org/2026.acl-demo.33.pdf) |

### 「可接受阈值」的依据（三类来源勿混用）

1. **人类基准约 200 ms**：Stivers 等 2009 PNAS 跨语言研究测得人类轮次转换**中位间隔约 200 ms**（[PubMed](https://pubmed.ncbi.nlm.nih.gov/19553212/)、[同行评议转引](https://wrap.warwick.ac.uk/id/eprint/187345/9/1-s2.0-S0911604424000393-main.pdf)）；轮次转换点间隔的 **0–1000 ms/50 ms 分箱实证分布**见 [SIGDIAL](https://preview.aclanthology.org/ingest-acl-2023-videos/2022.sigdial-1.20.pdf)。**[已核实]** 这是"越短越好"的依据，不是产品阈值。
2. **ITU-T G.114：单向 150 ms 阈值**（[ITU](https://www.itu.int/dms_pubrec/itu-t/rec/g/T-REC-G.114-200305-I!!SUM-HTM-E.htm)、[ACL 论文并引](https://aclanthology.org/2026.acl-demo.33.pdf)）。它只针对**网络传输延迟**，不含 ASR/LLM/TTS 计算——"G.114 = 端到端 150 ms"是**误引**。**[已核实]**
3. **HCI 实验**：车载语音助手研究结论为 **0.5–1 s 响应"generally acceptable"**，随任务复杂度变化（[Aalto](https://aaltodoc.aalto.fi/server/api/core/bitstreams/e6994489-ecaa-4206-8dec-a66b8d63a45b/content)）**[已核实]**。"sub-500ms"是**厂商口径**（[Vapi](https://vapi.ai/blog/speech-latency)），"sub-200ms"/"sub-800ms"同属营销断言（[Deepdub](https://deepdub.ai/post/voice-ai-latency-why-under-200ms-is-the-only-acceptable-standard)、[heise 访谈](https://www.heise.de/hintergrund/Interview-Menschen-nehmen-nicht-mehr-wahr-dass-sie-mit-einer-KI-sprechen-11212293.html)）；甚至有厂商公开提醒"同行的延迟数字不可信"（[SignalWire](https://signalwire.com/blog/ai-providers-lying-about-latency)）。

**两条可操作结论**：① **填充语能降低"感知等待"，即使真实延迟不变**（[ACM](https://acm-stag.literatumonline.com/doi/pdf/10.1145/3716553.3750792)）**[已核实]**——这就是"我查一下"话术的理论依据；② 设计目标应区分**掩盖延迟（masking）与塑造体验（shaping）**（[ACM](https://dl.acm.org/doi/pdf/10.1145/3841187)）**[已核实]**。**建议：p50 目标 800 ms，p95 红线 1.2 s。**

### 优化顺序（收益高度不均）

端点判定与 ASR 在朴素流水线里**串行**吃掉大部分预算。
**① 并行化**：流式 ASR 在 endpoint 判定**之前**把 interim 交给 LLM 做 speculation——双路投机生成（[RelayS2S](https://ar5iv.labs.arxiv.org/html/2603.23346)）、[端点预判](https://huggingface.co/papers/2606.13450)、推理与说话按 chunk 交错（[STITCH](https://browse-export.arxiv.org/pdf/2507.15375)）、异步 I/O + 投机工具调用（[arXiv 2605.13360](https://export.arxiv.org/pdf/2605.13360)）；厂商蓝图亦将 "speculative speech processing" 做成独立调优环节（[NVIDIA](https://github.com/NVIDIA-AI-Blueprints/nemotron-voice-agent/blob/main/docs/how-to/tune-pipeline-performance.md)）。
**② 预连接（pre-warm）**：真实工程报告显示**不预热时首轮延迟劣化约 2–3 s**（[openclaw #85847](https://github.com/openclaw/openclaw/issues/85847)）**[已核实：来自标题]**，性价比最高。
**③ 砍 endpointing ④ 首句特殊化（小模型/短切分）⑤ 最后才换供应商。**
**另一条路线**是放弃级联、用端到端全双工语音模型（如 [Moshi](https://ar5iv.labs.arxiv.org/html/2410.00037v2)），代价是可解释性、工具可控性与审计链路明显变差——**高风险场景不建议走**。

## 二、十大工程难点

**难点一｜延迟预算失控：串行流水线与「看不见的静音窗」**
*现象*：实测 p50 >1.5 s，但每个供应商 TTFB 都"只有 200 ms"。*根因*：三个隐性串行点——(a) endpointing 静音窗在**最前面**独占 300–700 ms，其后才开始计时；(b) 批式 ASR 等整段传完才返回，把 200 ms 放大到秒级；(c) 应用层在 WebRTC 抖动缓冲之上**又叠一层播放缓冲**，白付两份。*解决*：全链路流式 + speculation；用**一次端到端 span** 记录各段起止，而非分别信任供应商仪表盘。*代码*：
```python
clip = segmenter.take()             # 反模式：700ms 静音窗后才返回，之后四段全串行
text = await asr.transcribe(clip); reply = await llm.complete(text)
audio = await tts.synthesize(reply)
### 正解：interim 先喂 LLM，endpoint 只是「提交点」；首句阈值单独调小
FIRST_CHUNK_MIN_CHARS = 8
```

**难点二｜打断（barge-in）：「停掉播放」远不够**
*现象*：插话后 AI 还说半句；或停下后 LLM 上下文却记着"我说完了整句"；或 AI 被自己的回声打断。*根因*：打断是跨 5 层的**分布式取消**——① 客户端已缓冲的 200–500 ms 音频；② 在途 TTS 流；③ 在途 LLM 流；④ **对话状态**（"已生成 ≠ 已播放"，所有错乱的源头）；⑤ **声学回路**（扬声器声被麦克风拾取→VAD 判为用户说话→自我打断，靠 AEC；修复实例见 [hermes-agent](https://github.com/NousResearch/hermes-agent/commit/e1db388781935f24067d7c540fe0b18dcdb11e64)）。*解决*：状态机化（`LISTENING→THINKING→SPEAKING→INTERRUPTED`），取消**逐层下发并逐层确认**；引入假打断恢复（LiveKit 机制面：`resume_false_interruption`、`false_interruption_timeout`、`min_interruption_duration`、`min_interruption_words`，[Turn handling options](https://docs.livekit.io/reference/agents/turn-handling-options/)）；记录实际播放 `played_ms` 对齐服务端截断（Azure `conversation.item.truncate`，[API](https://learn.microsoft.com/en-ie/javascript/api/@azure/ai-voicelive/clienteventconversationitemtruncate?view=azure-node-preview)）；**"确认窗"模式**——要求连续有声语音达到一定时长/词数才认定真打断（[Glyphoxa ADR-0027](https://github.com/MrWong99/Glyphoxa/blob/v0.4.0/docs/adr/0027-barge-in-confirm-window-cancels-turn.md)）。*代码*：
```python
async def on_barge_in():
    played_ms = player.played_ms()      # 关键：先取实际播放位置
    await player.stop(); await tts_stream.aclose(); await llm_stream.aclose()
    await realtime.conversation_item_truncate(item_id, audio_end_ms=played_ms)
min_interruption_duration_ms = 300; min_interruption_words = 1   # 双阈值
```
截断须带 `audio_end_ms`，且**对已完成音频截断会报错**；更隐蔽的是**没发生打断时也会发 truncate**（[#2370](https://github.com/openai/openai-agents-python/issues/2370)）——所以"是否打断"必须由**你自己的状态机**判定。
*实测 bug*：两阈值互相覆盖失效（[#3515](https://github.com/livekit/agents/issues/3515)、[JS #785](https://github.com/livekit/agents-js/issues/785)）；假打断无法恢复（[#1229](https://github.com/livekit/agents/issues/1229)、[#4039](https://github.com/livekit/agents/issues/4039)）；恢复时输出不支持 pause（[社区](https://community.livekit.io/t/warning-resume-false-interruption-is-enabled-but-audio-output-does-not-support-pause/120)）；**被打断的话从历史丢失**（[#5038](https://github.com/livekit/agents/issues/5038)）；**"已静音但状态仍是 speaking"的取消死锁**（[#3418](https://github.com/livekit/agents/issues/3418)）；LLM 超时致重复播报（[#1238](https://github.com/livekit/agents/issues/1238)）；只播一个词就断（[#4486](https://github.com/livekit/agents/issues/4486)）；播放计数与实际不一致（[PR #4211](https://github.com/livekit/agents/pull/4211)）；截断报错（[PR #2374](https://github.com/openai/openai-agents-python/pull/2374)、[openclaw #125502](https://github.com/openclaw/openclaw/pull/125502)）；过于敏感致 AI 反打断用户（[#3427](https://github.com/livekit/agents/issues/3427)）。
*易漏*：用户说"嗯/对/好的"是 **backchannel**（表示在听），当打断处理会让 AI 反复闭嘴（[Deepgram](https://deepgram.com/learn/backchannels-vs-interruptions-voice-agents)）。厂商有更细停止策略（Vapi `stopSpeakingPlan`、Retell [背景噪声处理](https://docs.retellai.com/build/handle-background-noise)）。**建议**：backchannel 词表单独豁免，或仅在语义上是**新请求**时才认定打断。浏览器 AEC 演进中：Chrome 141 beta 让 `echoCancellation` 从只接受布尔值扩展（[Chrome 141](https://developer.chrome.com/blog/chrome-141-beta)）。

**难点三｜VAD 与轮次终结：固定静音窗必然误触发**
*根因*：**同一静音时长不可能同时满足"不抢话"和"不迟钝"**。句内与句间停顿的时长分布**高度重叠**：填充词的主要作用是**保持话轮（turn-holding）而非让出话轮**（[What makes a good pause?](https://ar5iv.labs.arxiv.org/html/2305.02101)）。厂商亦承认该模式：Azure 举例用户口述 `ABC-123-4567` 类**序号**时，分组停顿会长到被静音窗切断（[Azure](https://learn.microsoft.com/ar-sa/azure/ai-services/Speech-Service/how-to-recognize-speech?pivots=programming-language-csharp)）**[已核实]**；Azure 自己提醒静音超时"**只在观察到问题时才改**，处处是权衡"。
*参数建议*（Azure 可配区间 100–5000 ms、常见默认 500 ms 可作锚点）**[已核实]**：帧长 **20 ms**；起始静音窗 100–200 ms；最小话语长度 **200–250 ms**（本项目 250 ms）；**结束静音窗默认档 500 ms**（比 700 ms 跟手）；配语义模型后可降至 **300 ms**（高置信时 240 ms）；硬上限 30–60 s；pre-roll 200 ms；能量阈值取自适应噪声底 ×3。
*语义 endpointing 怎么做*：换判据——从"静音够不够长"换成"语义是否完整"。厂商已产品化：Azure Voice Live 的 **semantic VAD**（称嘈杂环境更稳健，[Azure](https://learn.microsoft.com/el-gr/azure/ai-services/speech-service/voice-live-api-reference-2025-10-01)）、OpenAI 把 `server_vad`/`semantic_vad` 作一等配置（[VAD 指南](https://developers.openai.com/api/docs/guides/realtime-vad)）。自建三档：① 轻量（ASR interim + 规则/小模型判句末，看有无"because/但是/如果"悬空）；② 主力（专门 EOT 模型，如 [LiveKit Turn Detector](https://huggingface.co/livekit/turn-detector)，按帧对"文本+音频"输出结束概率、可叠加在 VAD 上；官方称升级版使语音打断**减少约 39%**，[标题](https://livekit.com/blog/improved-end-of-turn-model-cuts-voice-ai-interruptions-39) **[已核实：来自标题]**；并已发布[公开 EOT 排行榜](https://livekit.com/benchmarks/eot-bench)）；③ 前沿（[分层 EOT](https://ar5iv.labs.arxiv.org/html/2603.13379)、[JAL-Turn](https://ar5iv.labs.arxiv.org/html/2603.26515)、[语音特征归因](https://arxiv-org.ezproxy.obspm.fr/html/2609.11066v1)、[Endpoint Anticipation](https://ar5iv.labs.arxiv.org/html/2606.13450)；证据显示**微调小模型优于 zero/few-shot 大模型**，[arXiv 2510.04016](https://arxiv.org/pdf/2510.04016v1.pdf)；多语言数据如 [TamilEOT](https://arxiv.org/pdf/2609.05631v1.pdf)）。声学+词汇融合确有增益：VAP 论文报告 **A+L+V 0.890 vs 仅声学 0.836（p<.05）**（[ACM](https://dl.acm.org/doi/pdf/10.1145/3716553.3750781)）**[已核实：数值原文]**。*代码*：
```python
if trailing_silence_ms >= cfg.silence_ms:            # 500ms 候选
    if turn_detector.p_end_of_turn(recent_text, audio) > 0.5: finish()
    elif trailing_silence_ms >= cfg.max_silence_ms: finish()   # 1.2s 兜底
```
**按场景切工作点**：数字/表单 1.0–1.2 s，闲聊用短窗。

**难点四｜ASR 错误的下游放大**
*现象*："改一下 `getUserMedia`"→"get user media"；"张翀"→"张冲"；金额不确定。LLM 拿错文本调工具，**错误被放大成真实副作用**。*根因*：通用 ASR 偏向常见词，专有名词/代码标识符/人名/数字在分布中稀疏；下游 LLM **没有"我不确定"通道**——错文本同样流畅可信，于是被当事实执行。数字更糟：ITN 的**歧义消解发生在 ASR 侧且不可逆**。已有工作考察下游对 ASR 错误的鲁棒性与实体级错误影响（[Interspeech 2023](https://www.isca-archive.org/interspeech_2023/li23s_interspeech.pdf)、[实体句错误分析](https://www.isca-archive.org/interspeech_2025/johnson25_interspeech.pdf)）。
*缓解（按性价比）*：① **热词/contextual biasing**——厂商面齐全（Deepgram [Keyterm](https://developers.deepgram.com/docs/keyterm)、Azure [phrase list](https://docs.azure.cn/pt-br/ai-services/speech-service/improve-accuracy-phrase-list)、Google [adaptation](https://docs.cloud.google.com/speech-to-text/docs/v1/adaptation)、AssemblyAI `word_boost`）。**收益可量化**：论文报告 Earnings-21 上加 biasing 后**实体短语召回 58.66%→79.11%（+20.45pp）**、F1 71.50→79.88（[arXiv 2603.16411](https://browse-export.arxiv.org/pdf/2603.16411)）**[已核实：数值原文]**；但**非万能**：社区反馈 keyterm"效果不稳"（[deepgram #1447](https://github.com/orgs/deepgram/discussions/1447)），且有预注册消融报告**提示级上下文对 WER 无可检测改善**（[arXiv 2608.28875](https://export.arxiv.org/pdf/2608.28875)）**[已核实：来自标题]**。**须用自己词表做 A/B。** ② **LLM 纠错**——用 N-best/confidence 让 LLM 在**已知词表内**纠错而非自由改写；实体级纠错有专门方法（[DeRAGEC](https://ar5iv.labs.arxiv.org/html/2506.07510)）。但 LLM 自身也会"不听话"：作为文本切分模型时**不遵循提示的比例为 gpt-3.5-turbo 9.7%、gpt-4-turbo 1.4%、gpt-4o 2.7%**（[arXiv 2408.00004](https://arxiv-org.ezproxy.obspm.fr/html/2408.00004v2)）**[已核实：数值原文]**——**关键数字勿只靠 LLM**。③ **拼音纠错（中文必备）**——同音/近音错字用拼音索引替换并打分，可参考 [Pinyin-Guided Chinese ASR with LLM](https://www.isca-archive.org/interspeech_2025/zhengjie25_interspeech.pdf)；代码标识符另建"英文读音→标识符"映射。④ **确认式复述**——高风险槽位必须回读，且**回读改变形式**（数字读中文、标识符逐字符念），避免习惯性"对"；"主动澄清"已被作为不确定性处理手段研究（[arXiv 2605.25404](https://export.arxiv.org/pdf/2605.25404)）。⑤ **ITN 双向校验**——金额/日期/电话做 normalize→denormalize→比对（[Data Driven ITN](https://arxiv.org/pdf/2207.09674)、[数值规范化](https://www.isca-archive.org/interspeech_2024/gupta24d_interspeech.pdf)），厂商可开关（如 Nuance `all_as_words`）；数字串用 `digit_run` 式精确匹配单独评测（[arXiv 2605.03073](https://ar5iv.labs.arxiv.org/html/2605.03073)）。*代码*：
```python
if any(w.confidence < 0.75 for w in result.words if w.text in sensitive_tokens):
    return clarify(...)                     # 不直接调工具
assert normalize(spoken) == asr.itn_output  # 数字歧义断言
```
且**须把 word-level confidence 传下去**。

**难点五｜语音工具调用：异步、超时与幂等**
*根因*：语音是**同步媒介**（期待即时回应），工具执行是**异步过程**；且语音**没有结构化确认 UI**，无法弹"确认/取消"按钮，于是要么不确认（危险），要么啰嗦口播（扰民）。Azure 文档明确工具执行是**轮次内作用域**：MCP 调用计时器"在调用完成**或用户打断时被取消**"（[Azure](https://learn.microsoft.com/tr-tr/azure/ai-services/speech-service/how-to-voice-live-mcp-server?view=foundry-classic&pivots=programming-language-python)）**[已核实：来自标题]**——**打断会顺手杀掉工具，须自行决定哪些允许被这样杀掉**。
*解决*：① **快速回执（0–1 s 内必须出声）**——实验已证明填充语降低感知等待，Azure 更把它做成官方特性（[interim responses](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-voice-live-interim-response)）**[已核实：来自标题]**；但这通常是应用层模式而非平台默认（[社区诉求](https://community.livekit.io/t/make-the-agent-announce-prior-to-calling-the-tool-functionality-not-available/1434)）。② **进度异步反馈**：阶段进展作为**可打断的插播**推送。③ **超时**：读 5 s / 写 30 s / 委派 coding agent 5–15 min（**厂商默认值无法证实，须自行设定并压测**），超时**明确播报**而非静默失败。④ **取消级联**：`kill` 进程组。⑤ **幂等**：副作用工具带幂等键服务端去重；写操作走临时文件+原子 rename、`--dry-run`、可回滚检查点；重试只对读与幂等写开放（[幂等消费](https://inngest.vercel.app/blog/your-agent-just-learned-to-spend-money)、[事务化工具调用](https://ar5iv.labs.arxiv.org/html/2602.14849)）。⑥ **确认分级**按 MCP annotations：`readOnlyHint` 直接执行、`destructiveHint` 必须确认、`idempotentHint` 允许重试。先例：Azure Voice Live"**部分工具需要用户批准**"（[Azure](https://learn.microsoft.com/id-id/azure/ai-services/speech-service/how-to-voice-live-mcp-server?pivots=programming-language-python)）**[已核实：来自标题]**；AWS Bedrock Agents 的 [userConfirmation](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-userconfirmation.html)；[Google HITL](https://docs.cloud.google.com/gemini/enterprise/docs/workflow-builder/use-hitl-steps)、[OpenAI approvals](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)。*代码*：
```python
@dataclass
class PendingConfirm:            # 独立状态机：不能靠 LLM 随口问
    tool_name: str; args: dict; idempotency_key: str
    expires_at: float            # 30s 未答 → 视为拒绝（fail-closed）
proc.kill()                      # 或 os.killpg(os.getpgid(proc.pid), SIGTERM)
```

**难点六｜语音驱动代码执行：高风险场景的最小安全设计**
*根因*：(a) 语音信道是**永不鉴权的开放输入**；(b) LLM 被授予**过高自主权**。有扎实文献与真实 CVE：语音助手侧有自动化"语音命令注入"（[LipFuzzer, NDSS'19](https://people.engr.tamu.edu/guofei/paper/LipFuzzer-NDSS19.pdf)、[车窗外声学注入](https://dl.acm.org/doi/10.1145/3719027.3765171)、[综述](https://dl.acm.org/doi/fullHtml/10.1145/3527153)）；语音驱动 LLM 有[不可感知听觉注入](https://ieeexplore.ieee.org/document/11573415)、[并发音频注入](https://arxiv.org/pdf/2607.28165)、[近超声越狱](https://zenodo.org/records/18402456)；代码执行侧已有真实 CVE——**GitHub Copilot CLI OS 命令注入 CVE-2026-29783**（[GHSA-g8r9-g2v8-jv6f](https://vulnerability.circl.lu/vuln/GHSA-g8r9-g2v8-jv6f)）**[已核实：来自标题]**、`git-mcp-server` 命令注入（[advisory](https://vulnerability.circl.lu/vuln/ghsa-3q26-f695-pp76)）。**指令与数据共用同一声学通道，语音入口天然放大 prompt injection。**
*最小安全设计（缺一不可）*：① **不可绕过的确认门**——破坏性操作必须经独立确认状态机，确认**包含将执行的具体内容**（"我要在当前仓库执行 `npm test`，确认吗？"）；**默认拒绝**，超时视为拒绝。参照 Claude Code：默认逐次批准、绕过需显式 `--dangerously-skip-permissions`（[权限文档](https://code.claude.com/docs/en/permissions)）。② **权限边界**：沙箱/容器、工作目录限定、网络默认关闭、只挂载必要路径、密钥不进沙箱、非 root（[Docker Sandboxes](https://docs.docker.com/ai/sandboxes/security/)）；风险框架见 [OWASP GenAI](https://genai.owasp.org/)（LLM01/Excessive Agency，**编号以官网为准**）、更贴题的 [OWASP Agentic AI Top 10](https://genai.owasp.org/2025/12/09/owasp-genai-security-project-releases-top-10-risks-and-mitigations-for-agentic-ai-security/)、[NIST AI RMF](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-ai-rmf-10)。③ **确认门本身也会被骗**：MCP 的 `readOnlyHint`/`destructiveHint` **只是"提示"而非强制**（官方文章标题即"[What Hints Can and Can't Do](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)"）**[已核实：来自标题]**，且存在**审批后改变行为的 rug-pull 攻击**（[Microsoft](https://learn.microsoft.com/en-us/security/zero-trust/catalog-ai-attack-techniques/rug-pull-attack)）与 tool poisoning（[OWASP MCP03](https://owasp.org/www-project-mcp-top-10/2025/MCP03-2025%E2%80%93Tool-Poisoning)）——注解只用于**分级默认值**，真正的门是**服务端策略 + 默认拒绝**。④ **来源隔离**：唤醒词 + 环境音检测，可选声纹；高风险操作要求多因子（口播一次性验证码），因声纹可被合成语音攻击。⑤ **命令白名单 + 结构化参数**：`run_shell` 不接受任意字符串，改为命令+参数数组，拒绝管道/重定向/`;`，做 `realpath` 前缀逃逸检查——直接消灭"ASR 错字→命令注入"。⑥ **审计与回滚**：记录音频引用、ASR 文本、确认内容、实际命令、退出码、diff；写前打快照；push/发布类要求**异渠道人在环**。⑦ **语音不是授权渠道**：绝不用"说一句密码"作长期凭证——可被录音重放。

**难点七｜并发与状态管理**
*根因*：语音会话是**长连接 + 有状态 + 多事件源并发**（麦克风帧、ASR partial、LLM token、TTS 音频、工具回调、客户端控制），而多数实现把状态放在**内存里的几个布尔变量**中，无单一权威状态机。*解决*：① **服务端权威 + 单写者**（一个 asyncio 任务/actor 持有状态，其他事件投消息）。② **会话恢复**：会话 ID + 事件序列号，重连重放未确认事件或拉权威快照——**音频可丢，文本轮次历史不可丢**；但恢复易成假象：有报告称重连**声称 `state_restored=True` 而 in-flight 状态并未恢复**（[pydantic-ai #7363](https://github.com/pydantic/pydantic-ai/issues/7363)）**[已核实：来自标题]**，以及"实时模型缺少自动重连/重置"（[livekit/agents #2341](https://github.com/livekit/agents/issues/2341)）——**务必自校验恢复状态，别信标志位**。③ **多用户隔离**：每会话独立命名空间，工具执行/记忆/临时文件全部隔离，**绝不共享可变全局**；多节点 WebSocket 扇出必须 **sticky session + 发布订阅适配器**（[Socket.IO](https://socket.io/docs/v3/using-multiple-nodes/)、[SignalR](https://learn.microsoft.com/en-us/aspnet/core/signalr/scale)），或把状态外置（[per-session 记忆存储](https://livekit.com/blog/mongodb-voice-agent-memory)）。④ **打断一致性**：维护 `generated_ms`/`sent_to_client_ms`/`played_ms`，**只有 `played_ms` 进历史**，截断幂等——真实事故正是"TTS 生成期间执行阻塞同步逻辑致用户打断不同步甚至丢失"（[#4183](https://github.com/livekit/agents/issues/4183)）。⑤ **容量**：单实例并发上限须实测（CPU 侧重采样/AEC），内存主因是连接数×缓冲（10 分钟 16 kHz mono int16 ≈ 19 MB/会话）；平台配额页存在但数值须自核（[LiveKit quotas](https://docs.livekit.io/deploy/admin/quotas-and-limits/)），长连接需按厂商要求**保活**（[Deepgram keep-alive](https://developers.deepgram.com/docs/agent-keep-alive)）。*代码*：
```python
self._inbox: asyncio.Queue[Event] = asyncio.Queue()   # 单一写者
if ev.turn_id != self.current_turn_id: return          # 丢弃过期事件
await store.save(session_id, snapshot, ttl=3600)       # 状态外置，支持重连
```

**难点八｜移动/浏览器端音频工程**
① **自动播放策略**：浏览器要求**用户手势**才能启动音频，`AudioContext` 可能以 `suspended` 创建，须在手势回调里 `resume()`（[Chrome 策略](https://developer.chrome.com/blog/autoplay)）；**把麦克风授权与首次播放解锁合并为同一手势**并显式提示"点击开始对话"；WKWebView 中 `AudioContext` 可能**根本无法 resume**（[WebKit 240646](https://wiki.webkit.org/show_bug.cgi?id=240646)）。② **安全上下文**：`getUserMedia` 只在 **HTTPS 或 localhost** 可用（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)）；http 下 `navigator.mediaDevices` 直接 `undefined`——"本地能跑、部署就哑"的头号原因。③ **采样率与重采样**：硬件常 44.1/48 kHz，ASR 多 16 kHz；`AudioContext` 采样率**绑定硬件**，路由/采样率变化会让 Web Audio 失真（[WebKit 154538](https://wiki.webkit.org/show_bug.cgi?id=154538)），Safari 上需**软件重采样**（[gglib #233](https://github.com/mmogr/gglib/issues/233)）——**要么在 Worklet 里做带抗混叠的重采样，要么直接请求 48 kHz 交给服务端；绝不裸线性插值**（混叠直接伤 WER）。④ **AudioWorklet**：`ScriptProcessorNode` 已被取代（[W3C 设计原则明文](https://www.w3.org/TR/design-principles/)），前者跑主线程、易丢帧；Worklet 内只做**采帧+环形缓冲+重采样**，不做网络/JSON；另注意 Chrome 对超过约 5 分钟未使用的后台标签**挂起 JS 定时器**（[Chrome 策略](https://support.google.com/chrome/a/answer/2657289)），采集与心跳不能依赖 `setTimeout`。⑤ **iOS Safari 特有**：WebKit 已记录多个真实缺陷——后台化后音频轨道 `ended`（[204681](https://wiki.webkit.org/show_bug.cgi?id=204681)）、**播放结束后 MediaRecorder 产出空录音**（[305827](https://wiki.webkit.org/show_bug.cgi?id=305827)）、媒体服务重置后 `getUserMedia` 持续报 `NotAllowedError: No AVAudioSessionCaptureDevice`（[319706](https://wiki.webkit.org/show_bug.cgi?id=319706)）；结论：**不要依赖 MediaRecorder**，改用 AudioWorklet 采原始 PCM；监听 `visibilitychange` 并在回前台**重连 + 重新 resume**；接受"iOS 后台无法持续拾音"。开麦录音还会把输出切到扬声器、影响 AEC 参考，原生侧需正确配置 AVAudioSession category（[Apple QA1754](https://developer.apple.com/library/archive/qa/qa1754/_index.html)）。⑥ **WebRTC vs WebSocket**：WS over TCP 有**队头阻塞**（[WebTransport 对比](https://websocket.org/comparisons/webtransport/)）；WebRTC 走 UDP+Opus，带 FEC/PLC、自适应抖动缓冲与拥塞控制（[IETF FEC 要求](https://datatracker.ietf.org/doc/draft-ietf-rtcweb-fec/)），弱网显著更好，代价是 TURN/STUN 与更复杂信令（[LiveKit](https://livekit.com/blog/why-webrtc-beats-websockets-for-voice-ai-agents)、[Azure Voice Live WebRTC](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/voice-live-webrtc)）。**建议**：消费端移动/弱网用 WebRTC；内网 demo 可用 WS，但须自实现抖动缓冲与重连。⑦ **Opus**：帧长可选 **2.5/5/10/20/40/60 ms**，RTP 封装由 **RFC 7587** 定义（`ptime`/`maxptime`/`maxaveragebitrate`）（[IETF](https://datatracker.ietf.org/meeting/79/agenda/codec-drafts.pdf)、[RFC 7587](https://www.potaroo.net/ietf/rfc-pdf/rfc7587.pdf)）**[已核实]**；推荐码率请查 Xiph [Opus Recommended Settings](https://wiki.xiph.org/index.php?title=Opus_Recommended_Settings)（本报告未读到数值，故不断言 16/24/32 kbps）。带宽可自算：**24–32 kbps ≈ 0.18–0.24 MB/分钟/方向**。

**难点九｜成本与容量**
三块中 **TTS（按字符/时长）单价通常最高**，ASR 按音频分钟、LLM 按 token（[Deepgram](https://deepgram.com/learn/why-elevenlabs-gets-expensive-at-scale)、[定价模型](https://deepgram.com/learn/voice-ai-pricing-models-per-minute-per-character-concurrency)）。量级锚点：**流式 ASR 约 $0.0043/分钟**（LiteLLM 价格表 `input_cost_per_second: 7.167e-05` 折算，[文件](https://github.com/BerriAI/litellm/blob/main/model_prices_and_context_window.json)）**[已核实：字段值]**；Google STT 约 **$0.003–0.016/分钟**、Azure STT 约 **$1/小时**量级（[标题](https://learn.microsoft.com/en-us/answers/questions/2155625/speech-to-text-costing-1-hr-is-crazy-no-bulk-avail)）**[已核实：来自标题]**；**TTS 基本按字符计费**（OpenAI `per_1k_chars`、Google 按"每月发送的字符数"），而**实时语音模型按音频 token 且很贵**——GPT-Realtime-2 音频输入 **$32/百万 token**、输出 **$64/百万 token**（[标题来源](https://m.163.com/dy/article/KSCBOC3K05198CJN.html)）**[已核实：来自标题]**。**价格随时变动，以官方页为准。**
**静音计费**：流式 ASR 按**流的秒/分钟**计费，"没说话的时间"照样花钱，VAD 门控直接省钱（但预门控可能伤 WER，是活的设计权衡：[Deepgram 讨论](https://github.com/orgs/deepgram/discussions/1216)）。**容量**：ASR/TTS 并发多为厂商**按并发流**限流（Deepgram 把"默认并发额度"当产品指标宣传：[三倍并发](https://deepgram.com/learn/tripling-default-concurrency-to-power-the-voice-ai-economy)；ElevenLabs 按并发排队并返回 429：[限流说明](https://elevenlabs.io/blog/ai-rate-limiting-for-voice)），须提前压测提额；单机瓶颈通常在**重采样 + VAD/AEC 的 CPU**。**长连接须保活+重连**：实时 API 的空闲 WebSocket 会被关闭（[openai-dotnet #274](https://github.com/openai/openai-dotnet/issues/274)）**[已核实：来自标题]**，且会话有**时长上限**（GPT Realtime 被报告为 30 分钟，[Q&A](https://learn.microsoft.com/en-us/answers/questions/5741275/gpt-realtime-maximum-session-length-30-minutes)；OpenAI 侧常引用 60 分钟，属**托管方相关**，须实测）**[已核实：来自标题]**。

**难点十｜可观测性与评测**
语音质量**只端到端有意义**——供应商只报自己那段， endpointing 静音窗、客户端缓冲、网络抖动都在其视野外；且语音 bug 高度依赖**具体录音**，没有回放不可复现。① **一次会话一个 trace、stage 级 span**（`user_speech_end → endpoint_fired → asr_final → llm_first_token → tts_first_byte → first_audio_played`），用 OTel GenAI 语义约定命名（[OTel GenAI](https://opentelemetry.io/blog/2026/genai-observability/)、[Langfuse×LiveKit](https://langfuse.com/integrations/frameworks/livekit)）；**限制：OTel GenAI 的音频/多模态 content-part 属性尚未标准化**（[开放 issue #304](https://github.com/open-telemetry/semantic-conventions-genai/issues/304)）**[已核实：来自标题]**，音频字段要自定 namespace；厂商侧可复用度量面： LiveKit metrics 的 `transcriptionDelay`。② **回归测试=录音回放**：真实音频 + 期望行为做成金标准集，CI 里对离线管线回放。**官方工具**：Pipecat evals 的 `EvalMicrophone` 把音频**注入**管线做确定性回放（[概览](https://docs.pipecat.ai/pipecat/evals/overview)、[API](https://reference-server.pipecat.ai/en/latest/_modules/pipecat/evals/transport.html)）；LiveKit 有官方 [agent 测试框架](https://docs.livekit.io/agents/start/testing/)；判分可用现成语音裁判（[openevals](https://github.com/langchain-ai/openevals)）；范式另见 [OpenAI Realtime Eval](https://developers.openai.com/cookbook/examples/realtime_eval_guide)、[三层测试法](https://futureagi.com/blog/three-layer-voice-testing-2026/)、厂商公开的[指标定义方法论](https://docs.vapi.ai/assistants/model-intelligence/metrics-methodology)。*代码*：`first_audio_played` 必须由**客户端上报已播放时长**、在服务端打点，否则永远测不到真实 TTFA：
```python
span.set_attribute("voice.ttfa_ms", played_at - user_speech_end_at)
span.set_attribute("voice.endpoint_reason", "semantic|silence_timeout|max_duration")
span.set_attribute("voice.asr.min_word_conf", min_conf)
```

**难点十一｜隐私与合规**
① **语音是个人数据且可能更敏感**——EDPB 明确认为语音数据**尤其敏感**（[EDPB 决定](https://www.edpb.europa.eu/sites/default/files/article-60-final-decisions/es_2010_10_right_to_erasure_transparency_and_information_decisionpublic_redacted.pdf)）；用于**声纹识别**则属生物识别数据，触发 GDPR **第 9 条**特殊类别（[Art.9](https://gdpr-info.eu/art-9-gdpr/)）与 DPIA 义务（[ICO](https://ico.org.uk/for-organisations/advice-and-services/audits/data-protection-audit-framework/toolkits/age-appropriate-design/data-protection-impact-assessments-dpias/)）；最小化/存储限制见第 5 条，删除权见第 17 条（[DPC](https://www.dataprotection.ie/en/individuals/know-your-rights/right-erasure-articles-17-19-gdpr)）。② **EU AI Act 第 50(1) 条**要求直接与人交互的 AI **必须让人知晓其在与 AI 交互**（[条文](https://artificialintelligenceact.eu/article/50/)、[欧委会指引](https://digital-strategy.ec.europa.eu/en/node/17084/printable/pdf)）——工程含义：开场必须有明确 AI 身份声明，且不因打断/跳过而省略；另注意第 5 ## 三、反模式清单

| # | 反模式 | 后果 |
| --- | --- | --- |
| 1 | 批式 ASR（等整段再识别） | 延迟 200 ms→1–3 s；无法 speculative |
| 2 | 打断只调 `player.stop()` | 生成侧未停；历史认为整句已说；下轮被残留污染 |
| 3 | 无 AEC / 回声抑制 | AI 听到自己→自我打断→循环 |
| 4 | 固定 700–1000 ms 静音窗且无语义判句 | 思考停顿被抢话（最常见负反馈），或整体迟钝 |
| 5 | 同时配两个打断阈值 / 把 backchannel 当打断 | 阈值互相覆盖失效（[#3515](https://github.com/livekit/agents/issues/3515)）；AI 反复闭嘴 |
| 6 | 打断后不把"被打断的话"写回历史 / 不做假打断恢复 | 上下文缺失致答非所问（[#5038](https://github.com/livekit/agents/issues/5038)）；一声咳嗽让 AI 永久闭嘴（[#1229](https://github.com/livekit/agents/issues/1229)） |
| 7 | 无打断却发 truncate / 对已完成音频截断 | 状态不一致、报错（[#2370](https://github.com/openai/openai-agents-python/issues/2370)、[PR #2374](https://github.com/openai/openai-agents-python/pull/2374)） |
| 8 | `run_shell` 接受任意字符串直接执行 | ASR 错字→命令注入；音频 prompt injection→任意代码执行（CVE-2026-29783） |
| 9 | 语音确认靠 LLM 随口问，或确认默认通过（fail-open） | pending 确认丢失→退化为默认执行，且无审计 |
| 10 | 只靠 `destructiveHint` 注解当安全门 | 注解非强制，且有 rug-pull / tool poisoning |
| 11 | 无幂等键的重试 | 重复转账/发信/push |
| 12 | 相信重连返回的 `state_restored=True` | 恢复是假象，in-flight 状态未回（[#7363](https://github.com/pydantic/pydantic-ai/issues/7363)） |
| 13 | 全量录音无限期留存且无告知 | PIPL 单独同意缺失、GDPR 违规、CIPA 诉讼风险 |
| 14 | 只信供应商 Dashboard 的 TTFB | 测不到 endpointing 与客户端缓冲这两块最大真实延迟 |
| 15 | 应用层再叠大播放缓冲 | 白付 100–300 ms；缓冲只应一层 |
| 16 | 用 `ScriptProcessorNode` / 在 Worklet 里做网络 JSON | 主线程丢帧爆音；音频线程阻塞 |
| 17 | 线性插值改采样率 | 混叠噪声直接抬高 WER |
| 18 | http 部署（非 HTTPS/localhost） | `navigator.mediaDevices` 为 `undefined` |
| 19 | 依赖 MediaRecorder 或假设 iOS 后台可持续拾音 | 空录音（bug 305827）、后台轨道 `ended` |
| 20 | 不处理自动播放策略 | 首句"没声音"，用户以为坏了 |
| 21 | 多用户共享可变全局状态 / 无 sticky session | 会话串音、跨用户泄漏、状态错乱 |
| 22 | 长连接不设保活/重连 | 空闲被关闭，用户看到"卡死" |
| 23 | 工具无超时无取消 | 用户以为掉线；改主意也无法停止 |
| 24 | 无热词表就识别代码标识符/人名 | 每轮纠错，工具调用参数错 |
| 25 | 关键金额/命令只依赖 LLM 纠错 | LLM 自身会不遵循提示（数字任务 1.4%–9.7%） |

## 四、可观测性指标清单

**延迟类**（按 stage 上报，不只报总数）：`voice.ttfa_ms`（用户说完→首个音频样本播放，**p50/p90/p95**，核心北极星）；`endpointing.delay_ms` + `endpoint_reason`（`semantic`/`silence_timeout`/`max_duration`，判断是否长期靠兜底超时工作）；`asr.finalize_ms`、`llm.ttft_ms`、`tts.ttfb_ms`、`transport.rtt_ms`、`playout.buffer_ms`。**首次响应与后续响应分开统计**（首句最慢，混算掩盖问题）。

**打断类**：`barge_in.success_rate`（≤100 ms 内停声比例）、`barge_in.false_rate`（VAD 触发但无有效词，**backchannel 单独计一类**）、`interruption.resume_count`、`truncation.error_count`、`truncation_without_interruption_count`（对应 #2370）、`agent.talk_over_count`（AI 打断用户）。

**ASR 质量类**：**word-level confidence 分布**（p5/p25/p50，不只均值）；低置信词命中**高风险实体**次数→确认触发率；离线 WER/CER 按领域分子集（专有名词、**数字串用 `digit_run` 精确匹配**、代码标识符）；`asr.empty_result_rate`、`asr.hallucination_rate`（静音段产出文本）。

**会话与业务类**：轮次完成率、`no_input_timeout_rate`、`retry_count`（用户重复同一诉求=没听懂）、任务成功率、工具成功率/超时率/取消率、**确认拒绝率**（过高说明确认扰民）、掉线/重连率。

**成本类**：每通话成本（ASR/TTS/LLM 分项）、TTS 字符数、**生成音频秒数 vs 实际播放秒数**（差值=被打断浪费的钱）、静音计费时长。

**告警建议**：`ttfa_ms.p95 > 1200`、`barge_in.false_rate > 15%`、`no_input_timeout_rate` 突增、`truncation_without_interruption_count > 0`、单通话成本 p95 超预算。

## 五、成本控制清单

1. **VAD 门控 + 修剪静音**：静音不上传不计费，同时降低 ASR 幻觉（本项目 `trim_silence` 已在做）；但预门控可能伤 WER，需实测。
2. **打断即停生成**：TTS 按字符/时长计费，**已生成未播放=纯浪费**；做真正的服务端取消，并把"生成时长/播放时长"作为成本指标。
3. **固定话术预生成/缓存**：问候、免责声明、"我查一下"用预录音频或本地 TTS；缓存键含语音+语速+标点。
4. **Prompt caching**：长 system prompt（人设+工具定义）显著占 token，缓存输入可大幅降价（[Anthropic 官方](https://claude.com/blog/prompt-caching)；倍数与 TTL 以官方页为准）。**稳定前缀放最前**、易变内容放最后以命中缓存。
5. **模型分层**：首句/闲聊/确认用小模型，仅复杂推理上大模型；精简工具定义（每个工具描述都是常驻 token）。
6. **按需升级 TTS**：交互用低延迟模型，仅最终播报/品牌语音用高保真。
7. **预连接与及时释放**：预热省下首轮 2–3 s（见难点一），会话结束立即释放以免空占并发配额。
8. **限制回复长度**：硬限首答 ≤2 句 + "需要详细说明吗？"按需展开，同时降 LLM 与 TTS 成本。
9. **自建 vs API 临界点**：并发稳定且高时自建可降本，但计入运维/扩容/合规成本（[成本分析](https://www.assemblyai.com/blog/open-source-speech-to-text-cost)）。
10. **成本打标签**：按 `会话/供应商/阶段` 打标，才能定位"这个月为什么贵"。

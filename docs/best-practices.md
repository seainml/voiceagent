## 0. 先看结论：十个决定成败的点

| # | 结论 | 依据 |
|---|---|---|
| 1 | **打断（barge-in）必须由传输层显式声明，不能从"有音频到达"推断** | 实测：推断式实现在每一轮都会自我打断 |
| 2 | **一句话由多个音频块组成，只有 `audio.end` 能结束一轮** | 实测：把每个块当一轮，会把句子切成 40ms 碎片 |
| 3 | **TTS 静默失败是最危险的故障模式，必须显式校验** | 实测：macOS `say` 对中文默认音色会输出 0 帧 WAV |
| 4 | **本地 ASR 必须预热** | 实测：faster-whisper 冷启动 23s，预热后 0s |
| 5 | **句子级流式切分是最大的单点延迟优化** | 实测：首包音频 1.8s（含 ASR 1.3s），而非等全文生成 |
| 6 | **没有 AEC 就必须半双工**，或者把打断阈值提高并加持续帧确认 | 实测：客户端 BARGE_GAIN=3.0 + 4 帧确认 |
| 7 | **语音提示词必须显式禁止 Markdown / 代码 / 冗长** | 两者：LLM 默认输出读出来是灾难 |
| 8 | **危险操作要"说出来再等"**，且这必须写进状态机，不是 UI 弹窗 | 两者：语音确认是唯一自然的授权动作 |
| 9 | **真实首包延迟只能由客户端上报** | 调研：服务端无法知道浏览器何时真正开始播放 |
| 10 | **ASR 错误不可消除，只能设计成可恢复** | 两者：实测把"上午"识别成"上五" |

## 1. 延迟预算：先量，再优化

人类轮次转换的中位间隔约 **200 ms**（Stivers 2009, PNAS）；ITU-T G.114 的 150 ms 是**单向网络传输**指标，**不是**端到端语音助手指标——这是最常见的误引。HCI 实验支持 **0.5–1 s 属于 acceptable**。

建议目标：**p50 ≤ 800 ms，p95 ≤ 1.2 s**（从用户说完到听见第一个字）。

### 本仓库实测的分环节耗时

在 Intel Mac（CPU int8 faster-whisper `base` + macOS `say`）上测得：

| 环节 | 实测 | 说明 |
|---|---|---|
| ASR（3.0s 音频） | **1261 ms** | 批式，占整个延迟的 1/3 |
| LLM 首 token | **2 ms** | echo LLM；真实云端通常 300–800 ms |
| TTS 首包音频 | **1768 ms** | 含上面两段，即 TTS 本身约 500 ms |
| **端到端（TS 提交 → 音频回传）** | **4000 ms** | 其中大部分是 ASR |
| macOS `say` 合成 1.92s 音频 | 580 ms | 约 3.3× 实时，足够用 |

**结论**：在本地部署里，**ASR 是最大瓶颈**，不是 LLM。优化顺序应是 ASR → 网络 → TTS → LLM。

### 各环节的优化手段（按性价比排序）

1. **预连接 / 预热**。实测 faster-whisper 冷启动 **23.2 s**，预热后首轮 0 额外开销。本仓库在服务启动时用后台任务预热（`ProviderBundle.warmup()`）。云端模型也一样：提前建立 HTTP/2 连接。
2. **句子级流式 TTS**。本仓库用 `SentenceSplitter` 在 LLM 还在生成时就把第一句交给 TTS，并**预取下一句**（在播放当前句时并行合成）。这一条把"等全文"变成"等一句"。
3. **流式 ASR 是下一个大杠杆**。本仓库目前是批式（`transcribe(整个 clip)`），这是明确的已知瓶颈，provider 接口已按可替换设计。
4. **先文本后声学**（inner monologue 思路）。在级联架构里，让 LLM 先输出文本、TTS 再合成，本身就等价于这个技巧。
5. **不要在停顿时急于回应**。见下一节。

## 2. 轮次终结（endpointing）：唯一需要按人调参的地方

**Full-Duplex-Bench 的核心发现是，现有对话模型普遍"过于急于回应"——在用户只是思考性停顿时就抢话。**

这与延迟优化天然冲突。本仓库的选择与理由：

```toml
[pipeline]
vad_silence_ms = 600      # 尾随静音多少毫秒算说完
vad_threshold = 0.015     # RMS 能量阈值
asr_min_utterance_ms = 250  # 低于这个时长的"话"直接丢弃（键盘声、咳嗽）
```

**为什么是 600 而不是 500 或 800**：500 ms 有厂商文档背书（响应更快），但学术证据指向"模型太急"。600 ms 是折中。**这是最值得按用户和麦克风单独调的一个参数**，建议：

- 说话慢、常思考停顿的人 → 800–1000 ms
- 指令式、快节奏使用 → 400–500 ms
- 嘈杂环境 → 提高阈值到 0.02–0.03，并保留自适应噪声基底

**必须做的三件事**（本仓库都实现在 `audio/vad.py`）：

1. **自适应噪声基底**：`noise_floor` 快升慢降，阈值取 `max(配置阈值, noise_floor × 3)`。否则安静房间调到刚好的阈值，一进会议室就全程触发。
2. **预滚（pre-roll）**：保留静音检测前的 200–300 ms 音频，否则第一个音素被切掉，ASR 会把"明天"听成"天"。
3. **最长话语硬上限**：60 s。麦克风被卡住时不会无限增长缓冲区。

## 3. 打断（barge-in）：四个必须同时做对的事

**"打断 = 停止播放"是错的。** 必须同时：

1. 立即停止音频（**客户端本地先停，不要等服务端往返**——否则体感是"卡了一下才停"）
2. 取消 LLM 流
3. **把已经说出去的内容记进历史**，否则下一轮模型会重复自己
4. 决定正在运行的工具怎么办（取消 / 让它跑完但结果丢弃）

### 本项目踩过的三个真实坑

**坑 1：从"音频到达"推断打断 → 每一轮都自我打断。**
用户这句话的音频帧，会在它自己的 turn 启动之后才陆续到达（`end_utterance` 建 turn，后续帧还在路上）。如果 `push_audio` 看到"busy"就打断，结果就是：**每一轮都在开始转录的瞬间被自己取消，转写结果被静默丢弃，助手答非所问。**

> 正解：打断是**传输层的事实**，由检测方显式声明。浏览器在 VAD 听到播放中的语音时发 `barge_in`；服务端从不推断。

**坑 2：`audio.end` 和 `audio.chunk` 的语义混淆 → 句子被切成碎片。**
一句话会分成几十个音频块。只有 `audio.end` 能结束一轮。把 `end_utterance()` 放进 chunk 分支，会让每个 40 ms 块都变成一轮，全部因"太短"被丢。

**坑 3：打断会把待确认的问题回答成"否"。**
确认过程中用户开口，是**在回答**，不是打断。本仓库把两者分开：`barge_in` 在待确认时只停音频、不取消 turn；`interrupt` 才是用户的显式"停下"。

### 没有 AEC 时的自打断问题

调研结论很明确：**自建语音链路最大的隐藏成本不是模型费用，而是"打断 + 回声消除"**。扬声器的声音被麦克风收回去，助手就会听见自己并不断打断自己。

本仓库的三层防御：

| 层 | 手段 | 参数 |
|---|---|---|
| 1 | 浏览器 AEC | `getUserMedia({audio:{echoCancellation:true}})` |
| 2 | 播放期间提高 VAD 阈值 | `BARGE_GAIN = 3.0`（需比正常说话响 3 倍） |
| 3 | 播放期间要求持续语音 | `BARGE_FRAMES = 4`（约 80 ms 连续） |
| 兜底 | **半双工模式** | UI 上一个「打断：关」开关；终端环境默认就是半双工 |

宁可让用户手动打断，也不要让助手自说自话。

## 4. 语音里的工具调用

### 4.1 确认门是状态机的一部分，不是 UI 弹窗

危险操作（执行命令、写文件、调用 coding agent）应当：**用一句短话说明要做什么 → 停下来等 → 听到"确认"才执行。**

本仓库的实现要点：

- 确认问题由工具调用**参数**生成，而不是泛泛的"是否继续"：
  `我要执行这条命令：echo hi。确认执行吗？`
- 答案可以来自**语音 / 按钮 / 终端**任一通道，session 不关心来源
- **单字回复必须精确匹配**：`嗯` 是确认，但 `嗯这个嘛我想想` 不是。用前缀匹配会把后者误判为"是"（本项目实际踩过）
- 模糊回答**再问一次**，而不是猜，也不是静默超时
- **超时即拒绝**（45 s）——需要确认的事，沉默不应等于同意

### 4.2 长任务不能沉默

调用 Claude Code / Codex / DSH 这类 agent CLI 可能跑几分钟。**必须先说一句话再执行**（"好的，我让 Claude Code 去处理"），并在过程中流式播报进度。本项目把工具进度事件和助手输出事件**合并到同一条有序事件流**，否则进度会从另一条路漏掉。

这三个 CLI 的非交互调用方式（**都已在本机实测**）：

| CLI | 命令 | 坑 |
|---|---|---|
| Claude Code | `claude --print --output-format stream-json --verbose "任务"` | 输出 JSONL；未登录时 `is_error:true` |
| Codex | `codex exec --color never --skip-git-repo-check --json "任务"` | **必须关掉 stdin**，否则它会等标准输入；不在 git 仓库里必须加 `--skip-git-repo-check` |
| DSH | `dsh --profile headless "任务"` | 最干净，纯文本输出 |

**统一给它们加一段前置提示**，要求最终用不超过三句口语总结——否则它们返回的 Markdown 会被原样读出来。

### 4.3 安全边界

- **默认拒绝**，而不是默认允许
- MCP 的 `destructiveHint` **只是提示、不是强制**，服务端策略才是真正的门。本仓库对 MCP 工具同时使用（a）注解、（b）名称启发式（`write`/`delete`/`exec`…）、（c）配置的确认列表
- shell 黑名单只是安全带，不是沙箱；**真正的控制是确认**
- 让被包裹的 agent CLI 绕过自身权限（`--dangerously-skip-permissions`）必须**显式开启**，默认关闭

## 5. ASR 错误：不可消除，只能设计成可恢复

实测把「明天上午十点开会」识别成「明天上五十點開會」——**"午"→"五"**。这类错误（数字、金额、人名、项目代号、代码标识符）无法靠换模型消除。

四层应对，按性价比：

1. **热词 / contextual biasing**（最划算）
   ```toml
   [asr]
   hotwords = ["voiceagent", "张三", "Kubernetes", "季度复盘"]
   ```
   把同事姓名、项目代号、CLI 名称塞进去，能修掉绝大多数真正让人恼火的错误。Whisper 系用 `prompt`，效果比换更大的模型明显。

2. **复述确认**（针对不可逆操作）
   提示词里明确要求："在执行难以撤销的操作前，把关键细节读回来确认。"

3. **提示词里承认识别不完美**
   ```
   如果请求不合逻辑，问一个简短的澄清问题，不要猜。
   如果用户纠正了某个词，本次会话后续都用纠正后的说法。
   ```

4. **LLM 纠错**（谨慎使用）
   让 LLM 修正明显不合理的转写。风险是它会把正确的专有名词"改对成"常见词，所以只对高置信度的类型（数字格式、常见搭配）启用。

## 6. 为"被听见"而写提示词

LLM 的系统提示词默认是为**阅读**优化的。直接用在语音上会输出 Markdown、代码块、四级标题和 400 字长文——这些东西通过扬声器是纯粹的噪音。

本仓库的提示词（`agent/prompt.py`）强制约束：

- **1–3 句短句**，除非用户明确要求详细
- **禁止 Markdown**：粗体、代码、项目符号、表格、标题一律不用
- **不朗读代码、文件路径、URL、长标识符**——说"我写在文件里了"/"详情在屏幕上"
- 采用用户的语言；用户说中文就用中文
- 不要"这是一个很好的问题"式开场

此外还有**代码级兜底**：`sanitize_for_speech()` 剥掉代码围栏、链接、emoji、表格；`truncate_for_speech()` 在句边界截断并补一句"更多细节在屏幕上"；`pipeline.max_spoken_chars` 给单轮朗读量设硬上限（默认 700 字）。

**"屏幕上/文件里"是语音助手最重要的一个逃生舱**：屏幕能承载的信息量远大于扬声器，不要试图把一切都说出来。

## 7. 可观测性：量你真正能感知的东西

必须埋的指标（本仓库全部实现并暴露在 UI 上）：

| 指标 | 含义 | 为什么需要 |
|---|---|---|
| `asr_ms` | 识别耗时 | 本地部署的头号瓶颈 |
| `llm_first_token_ms` | LLM 首 token | 用户感知"开始思考" |
| `tts_first_audio_ms` | **服务端**发出首包 | 便于定位是服务端慢还是网络慢 |
| `client_ttfa_ms` | **客户端实际开始播放** | **只有这个才是真实首包延迟** |
| `turn_total_ms` | 本轮总耗时 | 回归对比的基线 |

**关键点：服务端测不到真实 TTFA。** 只有浏览器知道 `AudioBufferSourceNode.start()` 何时真正发声。本仓库由客户端测量并回报（`{type:"metric"}` 帧）。

还需要监控的（本仓库暴露但未做持久化）：打断成功率、空转写率、确认拒绝率、工具失败率。

**录音回放测试**是性价比最高的回归手段：录一批真实音频，作为固定输入跑完整链路，比对转写与响应。本仓库的 `scripts/smoke.py` 用 TTS 合成探针实现了一个零素材版本。

## 8. 工程结构上的取舍

### 8.1 Provider 协议要小

三个 Protocol（`ASRProvider` / `TTSProvider` / `LLMProvider`）各只有 2–3 个方法。越小的接口越容易替换实现——本仓库因此能在**不改任何业务代码**的前提下，把 ASR 从 mock 换成 faster-whisper 再换成云端。

### 8.2 本地优先，云端可选

`auto` 解析顺序：**能离线就先离线**。

```
ASR: faster_whisper → openai(有 key) → browser(浏览器内置识别)
TTS: macos say → edge-tts → openai → mock
LLM: 有 key → 本地 endpoint(Ollama/vLLM) → echo
```

**"零密钥就能听到它说话"** 是产品级的体验差异：任何需要先配 key 才能验证的项目，都会在第一步流失使用者。`echo` LLM 让没有模型的用户也能完整验证语音链路（麦克风、VAD、打断、UI），并**用语音明确告知**还缺什么。

### 8.3 事件流只有一条

所有输出（助手增量、工具调用、工具进度、音频、指标）都走同一条有序事件流。**工具内部产生的进度事件也必须汇入这条流**——本仓库最初让工具进度走另一条回调，结果事件流不完整、无法测试。用队列把生产者和消费者解耦后，异常也能正确传播（否则会被吞在无人 await 的 task 里）。

### 8.4 半成品状态要能自愈

打断会留下"assistant 请求了工具但结果没回来"的历史。直接发给 OpenAI 兼容 API 会 400。本仓库在构造请求前做一次 `_sanitize()`：丢弃未被回答的 tool_calls 与孤儿 tool 消息，但**保留助手已经说出去的文字**。

## 9. 反模式清单

| 反模式 | 后果 |
|---|---|
| 从"有音频到达"推断打断 | 每轮自我打断，转写被静默丢弃 |
| 每个音频块都结束一轮 | 句子被切成碎片，全被判"太短" |
| 等 LLM 全文生成再合成 | 首包延迟 = 全文生成时间 |
| 播放期间不做任何 VAD 抑制 | 助手听见自己，无限自我打断 |
| 确认超时默认放行 | 静默即授权，安全门失效 |
| 单字确认用前缀匹配 | "嗯这个嘛…"被当成"是" |
| TTS 不做空音频校验 | 一切正常但没有声音，最难排查 |
| 把服务器错误吞在后台 task | 错误消失，用户只看到"没反应" |
| 不做 ASR 预热 | 第一句话多等 20 s，用户直接放弃 |
| 用文本提示词直接做语音 | 读出一堆 `**` 和代码块 |
| 靠 MCP 注解做安全 | `destructiveHint` 是提示不是强制 |
| 相信论文里的延迟数字可直接横比 | 口径不一致（是否含 VAD/网络/首帧播放） |

## 10. 测试策略

三层，缺一不可：

1. **全 mock 单元测试**（本项目 192 个，4.3 s 跑完）
   覆盖状态机、切分、VAD、工具护栏、协议帧。快、确定性、能测边界。

2. **协议级回归测试**
   针对每一个踩过的坑写一条：多块组成一句话、打断不误判、确认不被误答、空音频不静默。**这些测试的价值远超覆盖率数字。**

3. **真实端到端冒烟**（`scripts/smoke.py`，14 项检查）
   用真 provider：真实 TTS 合成 → 当作用户语音回灌 → 真实 ASR → 真实 LLM → 真实 TTS。还有真实 `dsh` 子进程调用、真实确认门、真实 WebSocket 往返。
   **本项目最有价值的一条测试**：TTS→ASR 闭环，它一次性抓住了"空音频静默失败"和"多块切分"两个 bug。

> 一条经验：**mock 测试证明逻辑对，真实闭环测试证明能用。** 只做前者会得到一堆绿色和一个不工作的产品。

## 11. 成本控制（云端部署时）

1. 先算每分钟，再比价——按 token 计价的实时 API（音频输入 $32/1M token）必须折算成 `$/分钟` 才能横向比较
2. **VAD 前置过滤**：静音不进 ASR，能省掉相当比例的调用
3. 缓存 TTS：固定话术（确认语、错误提示、"好的我处理一下"）预合成复用
4. 用便宜模型做首轮分类，只把需要推理的请求交给贵模型
5. 给 `max_spoken_chars` 设硬上限——既省 TTS 又提升体验
6. 长连接复用，避免每次请求重新 TLS 握手
7. 本地兜底：ASR/TTS 有本地后备，云端故障时降级而不是中断

具体厂商单价见 [框架生态调研](research/framework-landscape.md)。

## 12. 隐私与合规

- **默认不落盘**。本仓库默认不保存任何录音；只有显式开启才写
- 若必须留存：单独目录、明确保留期、可删除接口
- 端侧能做的（VAD、唤醒词）就不要上传
- 云端 ASR/TTS/LLM 会把语音内容送出本机——**在提示词里提醒用户**，至少要能在配置层面一键切到全本地
- 个人信息保护法 / GDPR：录音属个人信息，需要告知与授权；企业环境建议默认全本地链路
